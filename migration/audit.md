## 2. Content collections

One collection defined in `src/content.config.ts`:

| Collection | Loader | Base | Pattern | Body rendered? |
| --- | --- | --- | --- | --- |
| `post` | `glob()` | `src/data/post` | `*.md`, `*.mdx` | Yes — each post builds its own page |

**Schema fields (`post`):** `publishDate?` (date), `updateDate?` (date), `draft?` (bool), `title` (string, required), `excerpt?`, `image?` (string), `category?`, `tags?` (string[]), `author?`, `metadata?` (nested SEO object — title, canonical, robots, openGraph, twitter).

**Entries (6):** `astrowind-template-in-depth.mdx`, `get-started-website-with-astro-tailwind-css.md`, `how-to-customize-astrowind-to-your-brand.md`, `landing.md`, `markdown-elements-demo-post.mdx`, `useful-resources-to-create-websites.md`. Flat files (not folder-per-post) — no flattening needed.

**Consumption:** via `src/utils/blog.ts` (`fetchPosts()` → `getCollection('post')` → `getNormalizedPost()`), `getStaticPathsBlog*` helpers. `slug` is derived from `id` via `limax`; frontmatter has no `slug` field.

**Data files outside collections (editable site config — candidates for `data_config`):**
- `src/navigation.ts` — `headerData` (nav menu, dropdowns, actions) + `footerData` (link columns, social, secondary links, footnote). **TypeScript, not data** — editors can't edit `.ts` in CloudCannon. Decision needed in Phase 2: leave as developer-owned, or extract to a `.json`/`.yaml` data file.
- `src/config.yaml` — site name/URL, default SEO metadata, blog app settings (posts-per-page, permalink pattern, category/tag pathnames), analytics, UI theme. Consumed by the `astrowind` vendor integration → virtual `astrowind:config` module. **Good `data` config candidate** (YAML, already editor-friendly shape).

## 3. Pages and routing

**Static unique-layout pages (widget-composed `.astro`):**
`index`, `about`, `contact`, `pricing`, `services` (5) + `homes/{mobile-app,personal,saas,startup}` (4) + `landing/{click-through,lead-generation,pre-launch,product,sales,subscription}` (6) = **15 page-builder pages**.

**Markdown prose pages:** `privacy.md`, `terms.md` — both use `layout: ~/layouts/MarkdownLayout.astro`, long-form legal prose, `title` frontmatter only.

**System page:** `404.astro` — hardcoded, no editor value → leave as-is.

**Blog dynamic routes (`src/pages/[...blog]/`):**
| Route file | Helper | URL param source | Output |
| --- | --- | --- | --- |
| `index.astro` | `getStaticPathsBlogPost()` | `post.permalink` (from `POST_PERMALINK_PATTERN`, default `/%slug%`) | one page per post |
| `[...page].astro` | `getStaticPathsBlogList()` | `BLOG_BASE` (`blog`) | paginated list |
| `[category]/[...page].astro` | `getStaticPathsBlogCategory()` | category slug | paginated per category |
| `[tag]/[...page].astro` | `getStaticPathsBlogTag()` | tag slug | paginated per tag |

Permalink/URL logic in `src/utils/permalinks.ts` + `src/utils/blog.ts`. Post URL pattern is **frontmatter/derived `slug`** (via `glob` loader's id → `limax`), so the CC `url` for the `post` collection should use `/{slug}/` semantics driven by `permalink`, not the filename. Categories/tags are **derived from frontmatter values**, not their own collections (taxonomy — CC cannot manage these as collections; they regenerate from post frontmatter).

**RSS:** `src/pages/rss.xml.ts` (asset route).

## 4. Layouts, components & census

**Layout hierarchy:**
```
Layout.astro (base: head, CommonMeta, Analytics, Tailwind)
 └─ PageLayout.astro (Header + Announcement + Footer + <slot/>)
      ├─ index, about, contact, pricing, services, homes/*, blog routes
      └─ MarkdownLayout.astro (prose wrapper) → privacy.md, terms.md
 └─ LandingLayout.astro (minimal Header/Footer) → landing/*
 └─ Layout.astro (direct) → 404.astro
```
Metadata passed as `<Layout metadata={...}>`; blog posts merge post frontmatter into `metadata`.

**Widget components (page-builder block vocabulary)** — `src/components/widgets/`:
Hero, Hero2, HeroText, Note, Features, Features2, Features3, Content, Steps, Steps2, Stats, CallToAction, FAQs, Pricing, Testimonials, Brands, Contact (form), BlogLatestPosts, BlogHighlightedPosts, Announcement, Header, Footer.
All receive **inline props objects** in page frontmatter (`items[]`, `actions[]`, `stats[]`, etc.) — no external data source. This maps cleanly onto a CloudCannon page-builder `blocks` array of structures.

**Image handling:** mix of `~/assets/images/*` (optimized via `astro:assets`/Sharp — must stay in `src/assets/`) and remote Unsplash URLs routed through `src/components/common/Image.astro` (uses `unpic`). Upload path config in Phase 2 should target `src/assets/images/`.

**Icons:** `astro-icon` with iconify sets `tabler:*` and `flat-color-icons:*` (configured in `astro.config.mjs`). **No `src/icons/` directory exists** — fine because no `local:` icons are referenced, but create an empty `src/icons/` as a precaution against `Unable to load the "local" icon set!` during CC builds. `astro-icon` is compatible with `editableRegions()`.

## 5. Build pipeline

- **Build command:** `npm run build` → `astro build`. Output dir: `dist`. (Matches `netlify.toml`.)
- **No separate pre-build scripts.** The `astrowind` vendor integration (`vendor/integration`) runs at `astro:config:setup`: reads `src/config.yaml` → builds a virtual `astrowind:config` module + injects `site`/`base`/`trailingSlash`. CloudCannon's standard `astro build` reproduces this automatically.
- `astro.config.mjs`: `output: 'static'`, `~` alias → `./src`, image `domains: ['cdn.pixabay.com']`, MDX + sitemap + icon + compress.
- **Env vars:** none required for build (analytics id is null in config).
- **Install:** `npm i`. Preserved: `node_modules/`.

**1 of 3 thresholds tripped** → the 2-of-3 rule for mandatory sectioning is **not met**. A single-pass migration is acceptable; `migration/plan.md` is **not required**.

**However**, the conversion count (17) is high and the page-builder work in Phase 4 (visual editing across ~22 widget block types + scroll-reveal patching + component registration) is the most context-hungry. **Recommendation:** run Phases 1–3 in this conversation, then **start Phase 4 in a fresh conversation** to keep visual-editing quality high. The shape, if chunked, is **horizontal (per-phase)** — the 15 page-builder pages are uniform (same widget vocabulary), so one mental model per phase is efficient.
